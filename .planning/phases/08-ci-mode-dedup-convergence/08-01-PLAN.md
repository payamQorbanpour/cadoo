<objective>
Part A — carry `StructuralKey` end-to-end so `resolveStalePriors` stops resolving Cadoo's own
still-valid multi-line threads. This is the acute fix for the runaway loop and is foundational:
the same corrected `resolveStalePriors` logic serves both the CI memory-store path and the
DB-backed worker path.

Purpose: Today `resolveStalePriors` reconstructs each prior's `StructuralKey` from `p.Title`
(only the first line of the body), while current-run keys are built from the full body. For
multi-line comments the keys diverge, so every still-valid thread looks "stale" and is
auto-resolved (~37/39 threads). Threading the real key through fixes this in both backends.

Output: `PostedFinding.StructuralKey` field, `ListPostedFindings` selecting `structural_key`,
`memoryStore.list` populating it, and `resolveStalePriors` doing a direct compare with a
legacy fallback. Plus a regression test proving a multi-line finding is not self-resolved.
</objective>
